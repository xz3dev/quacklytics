Quacklytics uses two kinds of SQLite databases, and each has its own migrations:

| Scope | File | Migrated when |
| --- | --- | --- |
| `app` | `/data/app.sqlite` | When the backend starts (on the first API request) |
| `project` | `/data/projects/PROJECT_ID/project.sqlite` | When the project is opened, normally shortly after startup |

<Aside type="note">
    You normally don't have to do anything. Pending migrations apply automatically. The commands below are for inspecting state or rolling back.
</Aside>

## Commands

Stop the service, then run the CLI in a one-off container with the same volume:

```sh
docker compose stop analytics
docker compose run --rm --no-deps analytics bun run db:migrate status app /data/app.sqlite
```

The available commands:

```sh
# Show applied and pending versions
bun run db:migrate status app /data/app.sqlite

# Apply all pending migrations (or up to a target version)
bun run db:migrate up app /data/app.sqlite

# Revert one version
bun run db:migrate down app /data/app.sqlite

# Revert down to version 1 (the target is the version to KEEP; 0 reverts everything)
bun run db:migrate down app /data/app.sqlite 1

# Same for a project database
bun run db:migrate status project /data/projects/PROJECT_ID/project.sqlite
```

<Aside type="tip">
    Each command runs in a single transaction, so a failure rolls back everything that command changed.
</Aside>

## Rolling back

<Steps>

1. **Stop the service** and [back up](/self-hosting/backups/) the data directory.
2. **Run `down`** for the app database and for every project database that needs it.
3. **Deploy the matching older app version.** Starting the current version would re-apply its migrations.

</Steps>

<Aside type="danger">
    Down migrations can delete data. Never skip the backup.
</Aside>
